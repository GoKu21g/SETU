
Sahayogi Setu V2
Team roles and screen design guide
Who builds what, which persona each screen serves, and how every screen should be designed.
Based on: Sahayogi Setu V2 Detailed Blueprint (21 September 2026), Setu Website Audit: Sidebar Feature Line Inventory (21 September 2026), and the Setu design artifacts (visual blueprint, sidebar explained, app screens canvas).
Version 2, 28 September 2026. Updated and codified against the authoritative SetuV2-Layout reference implementation.
1. How to use this document
Every screen in Setu V2 exists because one of the 12 blueprint personas needs it. This guide gives each of the 7 team members a persona cluster, the screens they own, the live pages they must migrate or fix, and a design brief for each screen.
Read it in this order:
Section 2 for the design rules every screen follows.
Section 3 for the final navigation and which role lands where.
Section 4 for the team split.
Section 5 for your own member section and screen briefs.
Sections 6 to 8 for open decisions, the build process and the brief template.
Rule from the blueprint (§32.1): do not start from screens. Before drawing, each member confirms the data owner, states and permissions for their screen using the brief. The brief is the contract; the screen is drawn from it.
2. Design rules for every screen
2.1 Principles
Task first. Each screen answers its persona's question in the first view, before scrolling.
Every number drills down. A tile or count always opens the records, owner and next action behind it (blueprint §21, §33 decision test).
No privileged action without a reason. Any action that changes a customer, plan, access or data opens a reason dialog, writes an audit record, and asks for approval when policy requires (§1.1, §16.3).
Setu shows, it does not copy. CRM, invoices, tickets and HR stay in BoSS; logins stay in Sahayogi One. Screens link to them.
Mask personal data by default. Email, phone, PAN and GSTIN are masked unless the role has unmask permission; unmasking is audited.
Explicit states. Every record shows its state from the agreed state machine (§29), never a vague label.
No placeholders in production. No "Coming soon" banners, no pages without data sources in the navigation.

2.5 States every screen must design
Loaded with realistic sample data.
Empty: what it means and the next step, for example "No incidents in the last 30 days" (EmptyState component).
Loading: skeleton rows, animated pulse cards, never a blank page.
Error: what failed and a retry button, with the correlation ID for support.
Stale: last cached value shown with StaleIndicator warning when background polling fails.
No permission: the page explains which role is needed; never a silent blank.
Masked data: personal data (phone, PAN, GSTIN, secrets) masked with an audited unmask action.

2.6 Accessibility & Fluid Scaling
Real semantic HTML elements (buttons, links, inputs, labels); icon-only buttons always carry aria-label and title.
Text contrast at least 4.5 to 1 in both light and dark modes.
Fluid rem scaling ensures that all elements, padding, and text scale continuously when users zoom in/out or resize windows.
Full keyboard navigation, including Escape key to dismiss modals/popovers and Ctrl/Cmd+K for search.

7. How we build
7.1 Working rules
Fill the screen brief (Section 8) and get it reviewed before designing.
Build each screen as its own artboard file; only the lead merges into the shared canvas to avoid overwrites.
Start from the nearest built screen (Workspace 360, Operations inbox, Health or Audit explorer) and keep its layout and components.
Use the shared sample customers so screens connect into one story.
Wire the sidebar active state and cross-links (for example inbox item to Provisioning run) before review.
7.2 Order
Step
What happens
1. Contracts
Confirm owners, IDs, state machines (§29) and permissions for every screen. Settle open decisions.
2. Shell and foundation
Member 1 finalises sidebar and top bar with role visibility; Member 6 defines roles and audit fields every screen uses.
3. Screens in parallel
Members 2 to 7 build their screens from the briefs.
4. Connect
Lead merges artboards; links between screens are wired.
5. Review against personas
Walk each of the 12 personas through their question and the §33 acceptance tests.
